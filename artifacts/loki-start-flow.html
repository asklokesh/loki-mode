Loki Mode v8 · execution reference

What happens when you run loki start

A grounded walk through the pipeline: one-time setup, the RARV loop that repeats until the work is verifiably done, and the gates that decide "done." Numbers below are the shipped defaults, read from the source.

01The flow, end to end

Setup runs once. The middle band repeats: each pass is one iteration. The loop only exits when the completion council agrees the work is done, or a hard limit trips.

1

Resolve the spec

Detect what you passed: a PRD file, a GitHub/Jira issue ref, or an API contract. A contract (OpenAPI/GraphQL/Postman) is expanded into a per-operation checklist. No file? Loki reverse-engineers a PRD from the codebase.

cost free / localtime seconds
2

Preflight and checkpoint

Detect complexity (simple / standard / complex), pick the phase plan, snapshot a checkpoint and record the run-start git SHA. This SHA is what the evidence gate later diffs against to prove something shipped.

cost free / localtime seconds
↻

Enter the RARV loop

The core. Each iteration builds a prompt (spec + memory + phase + checklist status), calls the model, then runs post-iteration checks. Repeats.

↻ repeats per iteration · R → A → R → V
R

Reason · build the prompt

Assemble spec, retrieved memory, current SDLC phase, queued tasks, and checklist state into one prompt. Iteration % 4 == 0 uses the planning tier.

model planning tier
A

Act · the model works

The provider runs: writes code, edits files, runs tests, commits. This is the expensive step - the model call dominates wall-clock and cost. (v8: this can run on the Anthropic SDK instead of the claude CLI.)

model development tiercost $$ (dominant)
R

Reflect · verify the work

Checklist verifier maps each requirement to verified / failing / pending. The app runner boots the build and health-checks it. Playwright smoke tests run if it is a web app.

cost local + light model
V

Verify · gates + completion check

Every ~5th iteration (after a 3-iteration minimum) the completion council + evidence gate decide: is this actually done? If not, loop back with the findings injected into the next prompt.

model fast tier + reviewerscost $ (council)
↩ not done → next iteration (findings fed forward)
✗

The completion gate

Blocks "done" on: empty diff vs run-start SHA, red tests, an unhealthy serveable app (boot axis), or a leaked credential (secret axis). Any one failing keeps the loop running. This is the never-fake-green moat.

result pass → finish · fail → loop
✓

Finish and own

Write the Evidence Receipt (facts vs assessments), the proof-of-run, and the completion summary ("your app is live at ..."). The loop exits: complete, or max-iterations, or human stop.

cost free / localtime seconds

Completion cadence: the council runs at most every 5th iteration and never before iteration 3 (both configurable via LOKI_COUNCIL_CHECK_INTERVAL / LOKI_COUNCIL_MIN_ITERATIONS). 03Worth revisiting now that models are stronger

Honest read: these are opportunities, not measured wins. Several would need the parked benchmark (a real baseline) to size. Flagged by intent, not fabricated numbers.

Tune

Fewer, bigger iterations

Stronger models finish more per turn. The 4-step tier rotation and the ~5-iteration council cadence were tuned for weaker models - a stronger model may warrant checking completion earlier (interval 2-3) so simple builds exit in 3-4 iterations, not 8.

Tune

Collapse the tier rotation

All tiers already resolve to sonnet-5, so the R/A/R/V model switch is now mostly effort framing. Consider making it explicitly effort-based (planning=high, fast=low) rather than pretending to swap models.

Cut / simplify

Redundant re-verification passes

Checklist verify + app boot + playwright + council partly overlap. With a more reliable model, the belt-and-suspenders re-verify on every cycle can likely move to only the pre-completion check, saving a light model call per iteration.

Cut / simplify

Text-parse fallbacks

Several judge sites still keep a regex/text-parse fallback beneath the structured path. Now that structured outputs are reliable, the fallbacks are dead weight to maintain (though they are the fail-closed safety net - remove only with a measured green).

Keep

The evidence gate

Empty-diff / red-test / boot / secret axes. This is the moat and gets more valuable as models get more confident - a stronger model is more persuasive when wrong, so the deterministic gate matters more, not less.

Speed

Prompt caching + fewer spawns

The static prompt prefix (spec, memory) is re-sent each iteration. Real cache_control on the prefix would cut per-iteration token cost on multi-iteration builds. (Contingent: verify the CLI/SDK folds cache across per-iteration processes first.)

The honest efficiency picture: no CLI-vs-SDK or before/after speed numbers exist yet - the benchmark that would produce them is parked (needs billable baseline runs). The measured wins so far are on-path micro-optimizations (a council log tail-read went 67ms → 0.8ms; a checkpoint rebuild dropped ~50 process spawns to 1), not end-to-end build speedups. Treat the "time to completion" gains above as hypotheses to measure, not claims.
