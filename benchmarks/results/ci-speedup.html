Where the time actually was

Not the four full-tree find walks (120 ms total). It was 4,022 and 4,805 subprocess spawns -- one grep per file per pattern, now ~30 and ~130. System time fell 9.1 s to 0.5 s. For the linter, two files dominate: run.sh (24,305 lines) and loki (33,130 lines), each linted twice.

Two fail-opens caught, both of which looked green

Mine. Collapsing the linter's two invocations into one was 2x faster and silently lost 2 real failures -- severity prints on the caret line, not the header, and a file that cannot be opened emits no code at all. Found only by diffing counts against the original. Reverted; shipped pure scheduling instead.

The detectors lane. Its test-file classifier moved from an unanchored regex to an anchored glob, flipping paths like src/latest_thing.py from TEST to IMPL. A test-fitting commit then loses its test file, skips the blocking check, and exits 0 where it previously blocked. Its own evidence missed it: 316 byte-identical findings on this repo, where no such filename exists. Corpus-bound parity cannot detect a latent input-class narrowing.

Shell tests was 6x the next slowest job and set the pipeline wall clock by itself. Everything else finished inside ~2.5 minutes. The fix is a 4-way shard (LOKI_TEST_SHARD=i/n), splitting 289 suites as 73 / 72 / 72 / 72.

MEASURED, not projected. Observed shard timings on commit 9d63f16b: 5m35s / 2m33s / 3m50s / 2m26s. The pipeline wall clock is the slowest shard, so 13m01s became 5m35s: a 2.33x cut.

My earlier projection said ~3m15s and was wrong. It assumed the 289 suites cost the same each, so four shards would be a clean quarter. They are not: suite cost varies widely, the split is uneven, and the wall clock follows the worst shard rather than the mean. The projection is replaced here rather than quietly deleted, because a number that was published and turned out optimistic should be visibly corrected.

Safety, because a faster gate that stops noticing failures is worse than a slow one: tests/test-shard-coverage.sh (14/14) proves the shards partition the suite list exactly, that every suite lands in exactly one shard, and that an invalid shard spec exits non-zero rather than silently running nothing. The split was verified by executed counts, not arithmetic alone.

The fast tier covers syntax, structure and the entire trust core, and prints every check it deferred plus the command to run them -- without that, tiering would itself be a false-green. LOCAL_CI_TIER=full is required before push or release.
