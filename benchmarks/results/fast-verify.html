The same engine, three ways in. The CLI number carries shell and interpreter startup that an embedded caller does not pay, which is why the in-process and MCP paths are the honest figures for "plug this into your tool".

Why it was slow

The work was never the bottleneck. One detector performed four separate full-tree find walks (110 ms each) and spawned ~25 subprocesses at ~24 ms of interpreter startup apiece. git ls-files returns the same file set in 37 ms, already deduplicated and gitignore-aware.

What changed

Walk once and classify in that pass; run every detector as a pure function in a single process; cache findings by content hash so an unchanged file is never re-read and there is no staleness window to reason about; and scope to the diff, because verifying a change does not require reading the repository.

What is deliberately excluded

No model call and no network on this path, enforced by a test. Only checks the agent cannot author or influence. A verdict you can re-derive is a fact; a verdict a model produced is an opinion. That constraint is what lets this be embedded in someone else's product: they need to trust our arithmetic, not our model choices.

Baseline: tests/detect-mock-problems.sh 11,040 ms and tests/detect-test-mutations.sh 12,361 ms on the same machine. Correctness is asserted alongside speed in tests/test-fast-verify.sh (10/10), including no-false-positive cases, because a fast verifier that passes broken code is worse than a slow one.
