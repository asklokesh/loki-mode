## Quality Gates (8 gates; see `skills/quality-gates.md` for the canonical table)
1. Static analysis (CodeQL, ESLint)
2. Test suite pass/fail (red blocks; coverage % not measured in this release)
3. Blind 3-reviewer code review with severity blocking (Critical/High = BLOCK; Medium/Low advisory)
4. Anti-sycophancy / Devil's Advocate (on unanimous PASS)
5. Mock-integrity detector (HIGH blocks)
6. Test-mutation detector (HIGH blocks)
7. Documentation coverage
8. Magic Modules debate (ADVISORY by default on both routes; bash enforces only with `LOKI_GATE_MAGIC_DEBATE_BLOCKING=true`, Bun self-skips unless `LOKI_GATE_MAGIC_DEBATE="true"`)

Conditional auditor (not numbered): Backward-compatibility / legacy-healing-auditor (healing mode only - behavioral preservation, v6.67.0).

Note: unanimous APPROVE is required, and a reproduced blocking finding always
vetoes regardless of vote count. Every council/review agent pins its model
explicitly rather than inheriting the session model.

## v8 Harness Intelligence (v8.0.0)

Four measured-harness disciplines on the trust core. None can weaken a gate.

- **Prompt-cache discipline**: the prompt splits into a cache-stable
  `<loki_system>` prefix and a volatile `<dynamic_context>` tail at
  `[CACHE_BREAKPOINT]`. **Any new always-on instruction MUST go in the prefix**
  or it busts the cache every iteration.
  Two accuracy notes, because an earlier version of this bullet overstated it:
  explicit `cache_control` on that split lives in `sdk_invoker.ts` (the raw-SDK
  judge path) and is **opt-in, default OFF** behind `LOKI_SDK_PROMPT_CACHE=1`.
  On the main agent path the Agent SDK's `query()` takes a plain string, so the
  split is not applied there and the SDK/CLI does its own caching internally.
  On the bash route the `[CACHE_BREAKPOINT]` marker is a documentation anchor
  that orders the prompt; it sets no `cache_control` header. The ordering rule
  above still matters on every route -- a stable prefix is what any cache, ours
  or the CLI's, can reuse.
- **Confidence-spike re-check**: removed. It lived only in the separate Bun loop
  (removed in v11.119.0); `LOKI_CONFIDENCE_SPIKE` and its `_DELTA` / `_MIN` have no reader.
- **Goal scoring** (`autonomy/run.sh`): flags a
  `COMPLETION_PROMISE` with no measurable target. Advisory only. Suppressed for
  an absent goal and in perpetual mode. `LOKI_GOAL_SCORING=0`.
- **Smart retry** (`loki-ts/src/runner/retry_class.ts`): exits early on a
  positively-identified permanent failure. **Fail-safe direction is
  load-bearing**: unrecognized failures stay TRANSIENT and retry as before; rate
  limits are explicitly excluded from the permanent set. Never invert this
  default. `LOKI_SMART_RETRY=0`.
- **Usage-limit pause** (`usageLimitOf` in `loki-ts/src/runner/retry_class.ts`,
  `USAGE_LIMIT_STOP` in `loki-ts/src/engine10/machine.ts`): an engine10 session
  that ends on a plan usage limit (the SDK parser's `[sdk-loop error: usage
  limit...]` line from the structural rate_limit frame, or the provider CLI's
  own stderr line) is session kind `usage_limit`, never a quota wait, a retry or
  a failure. The run stops at that session: the cut stage records no result, commit
  and seal never run, and the supervisor closes the run through the cancel path
  (outcome CANCELLED, `run.completed` `paused: "usage_limit"`), so the next
  `loki start` of the same task offers to resume it. The Reason line names the
  stage, the provider's limit line and its reset.

Observability: SDK failures emit a structured `capability_degraded` record to
`.loki/events.jsonl`; `.loki/app-runner/first-preview.json` records
time-to-first-preview write-once (bash route only).

## Phase 1 / RARV-C Closure Env Vars

Default-on on the bash loop: `autonomy/run.sh` runs them through `loki internal phase1-hooks` (`loki-ts/src/commands/internal_phase1.ts`) after code review. Set to `0` to disable (see `CHANGELOG.md` v7.x entries and `skills/quality-gates.md`).

- `LOKI_INJECT_FINDINGS` -- inject structured per-finding records into the next-iteration prompt; persists `.loki/state/findings-<iter>.json` after aggregation.
- `LOKI_OVERRIDE_COUNCIL` -- enable the 3-judge override council on a BLOCK verdict. Requires `LOKI_INJECT_FINDINGS=1` (operator setting only this var alone is a no-op).
  **The BLOCK-LIFT arm never adjudicates on the bash loop.** The Bun loop that ran it was removed; on the bash loop (`--engine legacy`) the override lands in a stub that returns `REJECT_OVERRIDE` for every record (`loki-ts/src/commands/internal_phase1.ts:215-227`). Counter-evidence is still parsed and an `override-<iter>.json` transcript is still written, so the feature looks live in the artifacts while never being able to lift a BLOCK.
  This fail-closed direction is DELIBERATE, not a bug: on the agent-authored route the gated agent writes its own counter-evidence, so mechanical verification is forgeable. On bash the only exits from a Critical/High BLOCK are to fix the finding or to use the human-escape path (`rm .loki/PAUSE`). Documented here because the heading above says "default-on" and, for this one knob's block-lift, that is not true.
- `LOKI_AUTO_LEARNINGS` -- auto-write structured learnings per code_review cycle. Optional `LOKI_AUTO_LEARNINGS_EPISODE=1` also writes the learning into the episode store.
  Read by `internal_phase1.ts` (`LOKI_AUTO_LEARNINGS !== "0"`), which `autonomy/run.sh` calls through `loki internal phase1-hooks`; the variable itself never appears in `run.sh`.
- `LOKI_HANDOFF_MD` -- write a structured handoff doc before iteration close.
- `LOKI_REVIEW_ADVISORY` -- default on (`0` restores blocking). architecture-strategist, maintainer-mergeability and test-coverage-auditor are mandatory to run, not to block: they still run and their findings are recorded (`advisory: true` per reviewer plus `advisory_critical` / `advisory_high` in the review `aggregate.json`, one display-only row in the Evidence Receipt), but they carry no veto. `has_blocking` ignores them; security-sentinel and the other reviewers still block. maintainer-mergeability and test-coverage-auditor are routed to haiku at every tier. Implemented by `_is_advisory_reviewer` in `autonomy/run.sh`.

These knobs together implement the RARV-C (closure) loop: findings -> override council -> learnings -> handoff. Reference: `skills/quality-gates.md`, `CHANGELOG.md` entries from v7.x for default-on flip and override-council semantics.

## engine10 sizing knobs (`loki-ts/src/engine10/sizing.ts`)

- `LOKI_E10_SMALL_NO_RUNNER` -- default on: a missing test runner no longer disqualifies a task from "small". A small task skips the plan session (the implementer plans) and the skipped plan writes `plan-scope.json` from the files the task names. Set to `0` to make a missing runner force "normal".
- `LOKI_E10_SMALL_MAX_CHARS` -- task text length above which a task is not small (positive number, default 600; an invalid value falls back to 600 with a stderr note).
- `LOKI_E10_SCAFFOLD` -- release-note fragment writer (on by default; `=0` opts out). Right before the first verify, when the implement stage ended `done` and the repo keeps changesets (`.changeset/config.json`) or towncrier fragments, and the diff carries no fragment, Loki writes one with no model call: the package of each changed file (public workspace packages only, config `ignore` honored) or `<issue>.<type><ext>` named from the task number and the repo's own fragments, the body from the task title plus one sentence of the implement summary, quote style and trailing period from the newest real fragment. Nothing is written when the task says no changelog, the title is an internal change (chore, refactor, docs, ci, deps), only tests or docs changed, or the type or issue number is unclear; `changeset status` / `towncrier build --draft` remove a fragment they reject. Emits `scaffold.applied`. Whenever it writes a fragment, the receipt (not-proven list) and the PR body both say: "Loki added <path> as the release note for this change; delete it if this change needs no release note (LOKI_E10_SCAFFOLD=0 turns this off)." (`fragmentNoticeLine`). Code: `writeReleaseNoteFragment` in `loki-ts/src/project_model/conventions.ts`; tests in `tests/min/context-pack.sh`.
- `LOKI_E10_CHANGELOG_CONVENTION` -- on by default, `0` opts out (CL; `changelogFileConvention` in `loki-ts/src/project_model/conventions.ts`, reached through `releaseNoteConvention`, so it feeds the same per-run "Release-note convention" brief line after the cache-stable prefix). When the repo keeps no fragment convention (changesets, towncrier, changelog.d, newsfragments, changie win, unchanged), a single changelog file (`CHANGELOG`, `CHANGES`, `HISTORY`, `NEWS` or `RELEASE_NOTES` with an md/rst/txt extension, at the root or in `docs/`) is the convention when the contribution guide or PR template (root, `.github/`, `docs/`) asks for an entry (a checklist box, must, please, add, update, include, entry ...) and the file has an unreleased section (a markdown heading, an underlined rst title, or a bare or linked "Unreleased"/"upcoming" title line). The line names the file, the unreleased heading and the first entry under it as the format example. Nothing fires when any guide clause says not to update the changelog, the only mentions are optional, suggested, generated or left to maintainers, a PR-body "Release Notes" section is the only mention, the file has no unreleased section, or its head says it is no longer maintained or points to a releases page. The changelog file is never written automatically (`LOKI_E10_SCAFFOLD` skips this kind). The failure: on fresh repos whose CONTRIBUTING or PR checklist requires a changelog entry, the brief named no convention, FIXED_RULES says to write no documentation, and the judge failed the diff for the missing entry (3 of 5 judge fails on the dev set); on the 20 tuning trees it fires on none.
- `LOKI_E10_SCAFFOLD_TRACE` -- on by default, `0` opts out (TR; `scaffoldRecord` and `releaseNoteSkipBlock` in `loki-ts/src/project_model/conventions.ts`, kept by `scaffoldNow` in `engine10/machine.ts` as `implement.scaffold_skipped`). When the repo has a release-note convention but the `LOKI_E10_SCAFFOLD` writer wrote nothing, the receipt carries `release_note_skipped` with the writer's reason (for example "towncrier: the task names no issue number and the repo does not use orphan fragments"). Omitted when a fragment was written, the diff already carries the fragment or changelog entry, or the repo has no convention, so other receipts hash the same.
- `LOKI_E10_TOWNCRIER_ORPHAN` -- on by default, `0` opts out (TO; `towncrierOrphanPrefix` in `loki-ts/src/project_model/conventions.ts`). A task with no issue number gets an orphan fragment `<prefix><slug>.<type>[.<ext>]` when the repo uses orphans: its towncrier config sets `orphan_prefix` (that prefix is used), or any fragment in the directory already starts with "+". Before, only a newest example that was itself an orphan counted. A repo with no orphan in use still gets nothing, and TR records why.
- `LOKI_E10_TOWNCRIER_NEW_ORPHAN` -- on by default, `0` opts out (TN; `towncrierNoNumberPrefix`, `orphanBriefClause` in `loki-ts/src/project_model/conventions.ts`). A fix whose task gives no issue or PR number still ships the towncrier fragment the repo requires, in towncrier's orphan form `+<slug>.<type>[.<ext>]`, even when the repo has no orphan fragment yet: the fragment writer writes it (when the change type is clear), the towncrier brief line says "name it with the issue or PR number the task gives; when the task gives none, use towncrier's orphan form ... and never invent a number", and the self-check's missing-fragment flag names the same form for the review turn. Only a config that disables orphans (`orphan_prefix = ""`) keeps the old skip. The failure: CONTRIBUTING requires `<PR number>.<type>.rst`, the writer skipped (no number), the review turn justified skipping ("needs the PR number, which can't be invented"), and the judge failed the missing fragment.
- `LOKI_E10_ORPHAN_RENAME` -- on by default, `0` opts out (ON; `renameInventedFragment` in `loki-ts/src/project_model/conventions.ts`, run after the self-check's review turn by `stripInventedReleaseRefs`). A towncrier fragment the run created under a number no input gives (the task gives none) is renamed to the orphan form with the repo's own prefix, slug from the task title, when the repo already has orphan fragments or sets `orphan_prefix`; the receipt lists it under `changelog_refs_removed` ("renamed <old> -> <new>"). Otherwise nothing moves and the self-check's release-note item flags it ("numbered N, a number the task never gives; rename it to the orphan form ...") for the review turn. The failure: a run created a numbered fragment although no input carried that number.
- `LOKI_E10_CHANGELOG_FROZEN_STRICT` -- on by default, `0` opts out (FS; `logFrozen` in `loki-ts/src/project_model/conventions.ts`). The CL rule treats a changelog as frozen only when its first 15 lines say so in words ("no longer maintained/updated", "this file has been/is deprecated", "not maintained"), or when it has no unreleased section. The failure: the first rule also matched a bare "Deprecated" and "releases page", so a Keep a Changelog file with a "### Deprecated" subsection under Unreleased got no line. Off: that loose rule.
- `LOKI_E10_RUN_OUTPUT_DROP` -- on by default, `0` opts out (RO; `runOutputs` in `loki-ts/src/e10ext/commit_filter.ts`, part of `dropSet` beside GB, named on the receipt with the GB note). A deterministic filter before commit, never a model judgment: an ADDED file under a `.loki/` or `.loki-*` directory at any depth (the root one was always dropped), under `test-results/`, `playwright-report/`, `blob-report/`, `coverage/`, `htmlcov/`, `.nyc_output/`, `.pytest_cache/`, `.mypy_cache/`, `.ruff_cache/`, `.tox/` or `.hypothesis/` anywhere, or a JUnit report, `*.log`, `.coverage`, `lcov.info`, `coverage.xml` or `nohup.out` file, never reaches the delivered diff. Kept: the task names the file, or that directory holds a file tracked at base. The self-check's stray-files item records these as `auto`. The failure: on held-out repos the top review-fail class was stray committed run artifacts (test-results output and nested `.loki` logs).
- `LOKI_E10_CHANGELOG_REF` -- on by default, `0` opts out (CR; `changelogRefStyle`, `releaseNoteProblems` and the CL brief line in `loki-ts/src/project_model/conventions.ts`; checked by the self-check's release-note item). The reference form most existing changelog entries use (a markdown issue/PR link, `(#N)`, an rst `:pr:` role, `GH-N`, bare `#N`; at least 3 of the first 40 bullets and at least half) goes into the CL brief line with "use the number the task gives in that form, and never invent a number". The self-check flags an added entry that cites a number the task does not give, an entry with no reference to the task's number when existing entries carry one, a changeset naming a package no changed file belongs to, and a towncrier fragment numbered differently from the task's issue; a flag starts the self-check's review turn. After that turn a deterministic pass (`stripInventedRefsInFile`, `stripInventedReleaseRefs` in `features/self_review.ts`) removes from every release-note line the run added each `#N`, `(#N)`, `[#N](url)`, issue or pull URL, `:pr:` role and `GH-N` whose number the task input never gives, and tidies what is left, so the entry falls back to the repo's no-reference form; the receipt lists each removal (`changelog_refs_removed`). Base lines are never touched. The failure: on held-out repos the second review-fail class was changelog entries with no PR or issue reference, or with the wrong package or issue number.
- `LOKI_E10_SELF_REVIEW` -- on by default, `0` opts out, `always` runs the turn on every run (SR; `loki-ts/src/features/self_review.ts`, called at the end of the implement stage after the named-sites check and before the Wall restore; the receipt carries `self_review`). The pre-delivery review self-check. Five deterministic items are computed on the implemented tree against base, with no model call: (a) a release note the repo's rules require (the CL, changeset or towncrier convention) and the diff lacks; (b) stray files: a run-added file in a directory the repo has never tracked (build output is recorded as `auto`, the commit filter drops it); (c) a source change with no test file in the diff; (d) format: `auto` when a configured formatter normalizes the changed files at commit, otherwise the style configs are named; (e) scope: edits to existing files outside every scope signal (`outsideScope`). When any item is flagged (or with `always`), one bounded resume of the implement session (suffix `-rv`, turn cap `LOKI_E10_SELF_REVIEW_MAX_TURNS`, default 12, the cost cap; skipped when the stage has under 60 s left) gets the flagged items, the CONTRIBUTING and PR template text (6000 characters) and the style config names, may edit the diff, must change nothing that already follows the rules, and ends with one `REVIEW <a-e>: ok|fixed|justified: <reason>` line per item. Each item is then settled: the after-turn check no longer flagging it reads `fixed`; a persisting flag reads `justified` only with a stated reason, else `unresolved`. A clean minimal diff starts no turn, so it is never touched and costs nothing. Verify and the commit stage run on the reviewed tree as usual.

## Pull request base and target (`loki-ts/src/util/base_guard.ts`, PR-BASE)

The label must describe exactly what the pull request merges. Three places hold that, all on one measurement (`prScope`: files from `merge-base(target, head)` to head, commits in `target..head`, against the run's `base_sha..head`).

- Start (`prBasePlan`, called by `engine10/supervisor.ts` before the header, pull request runs only). HEAD already in the target: nothing changes and nothing is fetched. Otherwise the target is fetched once and the run (a) starts from the target tip when the tracked tree is clean (intake creates `loki/<run>` from that commit; the user's branch is never moved), (b) with `--base-current` or `LOKI_BASE_CURRENT=1` builds on the current branch and targets it (`LOKI_PR_BASE` is set to the branch) when origin has the branch and HEAD is in it, or (c) exits 2 with the reason and two commands. A dirty tracked tree is refused by intake as before; a detached HEAD starts from its commit as before and the seal holds its label.
- Seal (`sealPrScope`, one open note in `engine10/stages/seal.ts`): a difference holds the label at PARTIAL and the receipt records `pr_base` (target, target_sha, merge_base, base_sha, pr_files, measured_files, pr_commits, measured_commits, mode, start_branch, line). The key is absent on a run that opens no pull request.
- Pull request stage (`prScopeGate` in `engine10/stages/pr.ts`, called first in `runPr`): the same measurement after fetching the target; a difference that appeared after the seal opens the pull request as a draft with the reason.
- `--base-current` / `LOKI_BASE_CURRENT=1` -- build on the current branch; the pull request targets that branch. Off by default.
- `LOKI_E10_START_FROM`, `LOKI_E10_PR_TARGET` -- set by the supervisor for its own worker (the commit to start from, the target ref); never inherited from the caller's environment.

## Worktree substrate (autonomy/lib/worktree_prep.py)

`prepare_worktree(source_repo, dest, branch, setup=None, base=None)` creates an isolated git worktree and returns `{path, base_sha, deps, left_out_changes, deps_skipped}`. The start point is `origin/HEAD` after a fetch (when a remote exists), else HEAD. Uncommitted edits in the source checkout are never carried or stashed; their count is reported as `left_out_changes`. An fcntl lock at `~/.loki/repos/<slug>.lock` covers fetch and worktree add. Dependencies: a `setup` command run in the worktree, else a copy-on-write copy of ignored top-level `node_modules`, `.venv`, `venv`, `vendor` (a dir holding absolute symlinks or editable finders is never copied: it (or whose copy fails, with the partial copy removed) is left out, named in `deps_skipped`, `deps` is `skipped`, and the session installs it; a declared `setup` still fails hard), else `none`. CLI: `python3 autonomy/lib/worktree_prep.py SRC DEST BRANCH [--setup CMD] [--base REF]` prints the result as JSON. Callers: `autonomy/lib/backlog.py` (logs skipped deps), `autonomy/lib/workspace.py` (passes the entry `setup`) and `dashboard/api_start.py`.

`loki backlog` uses it for every issue worktree (`<checkout>-backlog/issue-N`, logs in `<checkout>-backlog/logs`, kept receipts in `<checkout>-backlog/receipts`). Testing aid: `LOKI_BACKLOG_LOCAL_ORIGIN=1` (off by default) lets `loki backlog` run from a checkout whose origin is an absolute path to a local bare repository, so a rehearsal's branches and PRs go to that bare repository while the run still uses GitHub for the issue itself; any URL or non-bare path keeps the refusal.

## Repo card: what Loki knows about a repository (`loki-ts/src/e10ext/repomemory.ts`)

One mechanism, on by default, `LOKI_REPO_CARD=0` opts out (nothing read, nothing written, and the issue brief loses the one layout sentence below). No embeddings, no database, no model-written memory: every fact is something the harness ran.

- **Facts.** `setup`: the part of an issue run's proof script before its first `loki_http` / `loki_cmd` line (services through `loki_pg_start` / `loki_redis_start`, migrations, starting the product, the first record), kept only when Loki's own re-run of that script printed at least one check result, which happens only after the setup. `quirk`: each `# QUIRK:` comment line in that setup. `env`: the services the repository needs and the names the setup exports. `command`: the commands of verify checks that passed. Every fact records the base commit of the run (the facts were verified on that run's change, built on it, and every renderer says "a change based on <commit>"), a lockfile hash (sha256 over the tracked lockfiles in any directory, or the manifests when there are none) and the run.
- **What is refused.** A setup is not stored when the script calls no check, has fewer than 4 lines or more than 12000 characters before the first check, does not parse by itself (`bash -n`), still names a path of the machine after the repository path is replaced by `${LOKI_REPO_ROOT}`, or carries something shaped like a real provider credential. The generic secret redactor is deliberately not applied to a setup: it blanks the throwaway password and signing secret the script invents for its own empty database, and the recipe stops running.
- **Where.** The local copy is `~/.loki/repo-cards/<sha256 of the normalized origin URL, else the absolute path>/card.json` (directory 0700, file 0600), written by the seal stage after every issue run, so a fresh clone of the same origin reads it with no action from the user. `loki knowledge export` writes the same card to `.github/loki-repo-card.md` for a team to commit, so it travels with every clone, teammate, CI job and container. The path is under `.github/` because `.claude/` is ignored in real repositories (FireLater's own tracked `.gitignore` ignores it, so a card there would never reach a clone), and `.loki/` is ignored run state. Loki reads the file itself and puts it in the brief, so no provider has to load it; the command warns when git ignores the path. Loki never commits it. `.loki/memory/repo-card.md` (ignored run state) is a rendered mirror for the Knowledge tab. When both copies exist, per fact the one verified on the newer commit wins. A setup read from the committed file passes the same refusal test as a captured one (size, credential shape, machine path, `bash -n`) or is not read, and every fact from that file is labelled in the brief as "from the card committed in this repository, not run on this machine".
- **Use.** The implement stage of an issue run on claude appends the card to the brief's repository context (fixed order, no timestamps or run ids, so the bytes change only when the card or the lockfiles do), writes the setup to `$LOKI_SCRATCH/loki-setup.sh`, records `repo-card.json` in the run directory, `repo_card` in the implement data and a `repo.card` event. The brief tells the session to start its `loki-proof.sh` from the setup. The fixed sentence `SETUP_FIRST_LINE` (setup first, at the top level, `# QUIRK:` above a workaround) follows `PROOF_SCRIPT_LINE` in the issue brief.
- **Setup check.** A setup is verified on the change of the run that wrote it, so it can need something that change carried and a clean checkout lacks (measured on FireLater: every stored setup stopped at `npm run migrate` on a clean checkout, because each run had made its own fix to the migration files, and two later sessions spent 85 and 113 seconds finding it again). So on the next issue run Loki runs the stored setup itself on the checkout before the session (`runSetupScript` in `engine10/proof_rerun.ts`: the proof re-run's own runner, a new scratch directory, the user's connection settings blanked, the ownership cleanup, a 120 second cap). It starts beside the plan session and only reads the tree. A cut script has no meaningful exit status, so Loki appends one line that prints a per-run token: the setup reached its end only when that line printed. Three outcomes reach the brief as `Setup check:`. It ran to its end: use it as it is. It stopped and one edit gets it through: at seal the card also keeps, as `patch` facts, up to 4 of the run's edits to files that existed before it (30 changed lines and 2500 characters at most each; no test, document, lockfile or anything shaped like a credential), and Loki tries each alone, smallest first, after the plan and already-done sessions have ended: apply, run the setup, take it out again, so the tree is as it was whatever happens (an exit handler covers a crash mid-trial). Edits are never tried together, which keeps another issue's feature code out. The first that works is handed over as a fact Loki ran both ways, with the failing output, the diff and `$LOKI_SCRATCH/loki-setup-fix.patch`; the session applies it, Loki never leaves it applied. It stopped and no single edit helps: the last output only. A `patch` fact never leaves the machine: it is not written to or read from the committed card. Trials stop after 120 seconds in total; they run inside the implement stage, so their seconds (8 to 21 measured) count against its limit. The event is `repo.card` with `when: "checked"`. Verified on one repository only.
- **Staleness.** A fact whose lockfile hash differs from the checkout's is shown as "last verified on <commit> with other dependency files: check before trusting". A stored setup is dropped at seal when the run's proof script carried it (7 in 10 of its lines), exited non-zero and reached no check. A stored command whose check could not start this run is dropped.
- **Show.** `loki knowledge` (`--json`), and `loki doctor --repo` prints the same lines after the repo profile.
- **What it replaced.** `verified_command.json` (E-126): the brief read it on every run and nothing ever wrote it.

## Verdicts, composite receipts and the autonomy ladder (v11.7.0)
- Two sets: receipt verdicts (`engine10/types.ts` Verdict: VERIFIED, PARTIAL, ALREADY_SATISFIED, SPEC_CONFLICT, FAILED) and run outcomes (`engine10/output.ts` Outcome adds BUDGET_STOP, BLOCKED, STALLED, CANCELLED; exit ladder EXIT). Only receipt verdicts are sealed.

- Parallel units: `route.ts` maybeRunGroup defaults to `features/speed/run_group.ts`, which freezes per-unit acceptance (`features/contract.ts`), runs units, merges with `engine10/integrate.ts` and seals once via sealGroup.
- Lessons: every sealed run appends a receipt fact (`LOKI_AUTO_LEARN_PR`, default on) outside the receipt body; `implement.ts` injects lessons and relevant learnings inside the untrusted-data fence; `loki memory brief --task T` prints the same block. With `LOKI_ORG_GRAPH=1` (off) `implement.ts` also appends `orgKnowledgeBlock` (util/pr_lessons.ts, python3 by file path, 10 s cap, 1500 bytes) and records org_bytes/org_lines in lessons-injected.json.

- `LOKI_COMMIT_WALL` -- off by default, `1` publishes (J2; `util/check_result.ts` commitWallEnabled). Loki's own `loki_wall_*` acceptance files stay out of the delivered branch: a VERIFIED seal makes no Wall child commit and records `wall_kept: {files, sha256, cmds, sealed_dir}` on its data instead, and the WIP commit of an unsealed end (`e10ext/commit_filter.ts` commitUnsealedWork) resets them like other churn and removes a run-created one from the tree. The sealed copy stays in `runDir/wall`, and the receipt keeps its sha256 (`wall.files`) and the check's rerun command. On the tuning bench every published Wall file whose run passed hidden failed the judge (3 of 3). `=0` also drops the copy-integrity notes, as before; `=1` restores the publish below.
- Wall publish (FC-VERIFIED-PR-WITHOUT-ITS-TEST): with `LOKI_COMMIT_WALL=1`, on a VERIFIED seal only, `publishWall` (`util/check_result.ts`, called from `stages/seal.ts`) makes ONE child commit (trailer `Loki-Wall-Publish: <runId>`) of the SEALED Wall bytes (`runDir/wall`, hash-checked against `wall.files[].sha256`) that verify ran and passed (`publishableWall`). Before writing, the realpath of each Wall file's parent directory must be inside the repo, and an existing file or symlink is removed first. The child commit runs with hooks and signing OFF (the default `git()` call, no `userHooks`), so a pre-commit hook cannot add files or rewrite the Wall bytes. Afterwards the commit must touch exactly the published paths and each committed blob must equal the blob hash of the sealed bytes (computed in process, never read from the worktree); on any mismatch the child is rolled back (`update-ref` HEAD to the product head plus `read-tree`), nothing is published and a NOT PROVEN note is added. The receipt binds the PRODUCT head (head_sha, tree, diff_sha256 are computed before the child commit). A re-seal binds `HEAD^` only when HEAD's message has the exact trailer line for this run, HEAD touches only paths of this run's `wall.files`, and every blob sha256 matches (`wallChild`); a forged trailer is not enough. `util/seal_drift.ts` accepts a moved HEAD after head_sha as benign only when every commit after it is such a Wall publish commit (linear, trailer line for the receipt's run_id, only `wall.files` paths, blob sha256 equal to the sealed one); any commit after head_sha that carries this run's trailer but fails that check is head drift (UNCHECKED). Later commits without the trailer stay under the TEN-GATES-16 sealed-path overlap rule. The PR body gains an "Acceptance tests" section. Commit stage and `backstopCommit` still drop Wall files. `LOKI_COMMIT_WALL=0` restores the old behavior (nothing published).
